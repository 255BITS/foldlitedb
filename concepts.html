The model

Replay and ordering

Documents are immutable observations. Views are the changing state derived from them. Stable identity, ordered inputs, and exact computation definitions make that state recoverable.

Names are optional

add(payload) assigns an internal ID. Equal unnamed payloads still represent separate observations. A caller-supplied name tells the host that an identical repeated call refers to one observation.

An identical named retry skips mapping and keeps its original position, even after the source advances. Changing that name's payload is a conflict. Model a changing lifecycle by appending a new observation and folding its status. This identity model applies to the native portable host, the browser host, and the callback API.

Positions track a source

A position means “this document's offset in its source.” Automatic positions start at zero and follow that source's committed checkpoint. External logs can supply monotonically increasing offsets with gaps.

from foldlitedb import PortableDatabase, SourceOrderError

with PortableDatabase(":memory:") as db:
    first = db.add({"metric": "loss", "value": 4}, source="training.log", position=10)
    db.add({"metric": "loss", "value": 8}, source="training.log", position=40)
    assert db.add(first.payload, source="training.log", position=10) == first
    assert db.stats()["checkpoints"]["training.log"] == 40
    try:
        db.add({"metric": "loss", "value": 3}, source="training.log", position=30)
    except SourceOrderError:
        pass
    else:
        raise AssertionError("New records cannot arrive behind the checkpoint")

IDs and positions are scoped to a source. An existing source position can identify a replay without a caller-supplied ID; payloads and any supplied ID must match. Previously unseen positions behind the checkpoint fail.

Positions range from zero through 2**53 - 1. Avoid mixing automatic positions with external offsets unless they share the same progression. Source checkpoints advance in the same transaction as documents and view states.

Ingestion order is separate

Ordered portable views, such as the bundled catalogue, and Python OrderedFold process contributions in ingestion order within a key. Source offsets do not sort records across sources; timestamps do not reorder an existing fold. Applications choose domain order before ingestion and replay that order.

Portable maps receive document payloads only. Their host tracks IDs, source positions, deduplication, and ingestion order. Callback maps receive complete Document records and can inspect that metadata. Include needed domain metadata inside portable payloads.

The callback API's numeric Envelope has a separate ordering contract: declared source position plus deterministic source/identity/emission tie breaking. It does not imply that the portable metrics module or all custom views use envelope ordering.

Keep the source outside the cache

Retain resolved documents and exact computation artifacts outside derived storage. Native documents() and browser export() expose retained records, but exporting a copy is the application's responsibility.

from foldlitedb import PortableView

view = PortableView.bundled("metrics")
with PortableDatabase("live.db", view) as live:
    live.add_many([
        {"metric": "loss", "value": 4},
        {"metric": "loss", "value": 8},
    ])
    retained = tuple(live.documents())
    expected = [(r.key, r.state, r.result) for r in live.rows()]

with PortableDatabase("rebuilt.db", view) as rebuilt:
    rebuilt.ingest(retained)
    assert [(r.key, r.state, r.result) for r in rebuilt.rows()] == expected
    assert rebuilt.ingest(retained).replayed == 2

Keeping payloads alone and assigning new identities does not preserve the source replay contract. It can also change callback computations that inspect document identity or numeric envelope tie positions. A label for a lost taxonomy or reference snapshot cannot reproduce its contents.

Portable add implementations must give equivalent results for the same ordered contributions split across successive batches. Preserve batch boundaries if exact engine sequence values matter: a sequence includes committed document and group-state records. Replayed databases have new identities and cursors even when their computed states match. Browser replay() retains the original batches and compares keys, states, and results.

Module changes and callback versions

Portable views: the SHA-256 digest identifies the complete compiled map, reducer, state schema, and SDK runtime. Native storage reopens only with the exact same bytes. Changed modules require a fresh database plus retained-document replay. Update the view version for changed behavior and the state version for incompatible formats; rebuild the manifest too. Matching labels do not override a different digest. Compiler changes can also alter the digest.

Python callbacks: View.version identifies map behavior; the fold and reducer have their own versions, and references declares captured external inputs. Registering a compatible definition reuses checkpoints. A changed definition rebuilds that callback view atomically from retained documents and invalidates its old cursors. Changing a callable or captured input requires updating its declared definition.

Python callbacks are trusted application code. Portable modules have no host imports and run with bounded memory and execution, but they must still be deterministic: use explicit inputs and state rather than mutable global data. Hosts instantiate portable modules afresh for operations. Neither path automatically makes arbitrary state mergeable.

Native persistence and browser memory

PortableDatabase uses the Rust engine's SQLite WAL storage. Documents, source checkpoints, states, and history survive a close and reopen. Different native connections coordinate writes through SQLite. The callback API uses a separate Python/SQLite schema; its files and cursors are not interchangeable with portable storage.

The browser host executes the same Wasm computation, while JavaScript retains documents, grouped states, and history in a dedicated worker. It currently uses no IndexedDB or persistent browser database. Reloading the page, closing the client, or a worker deadline discards state. Export resolved records before closing, then ingest them into a new worker to restore the view.

Native storage grows with retained documents, keys, and history. The browser preview instead rejects batches that exceed its document, key, history, and byte limits; see exact component limits. A 16 MiB Wasm linear-memory limit is not a limit on the entire host process.

Atomic commits and stable reads

A batch commits identities, checkpoints, reduced states, and change records together. A validation, map, reducer, or limit error rolls back the whole current batch. ingest_many commits separate batches as you iterate; earlier successful batches survive a later error.

A snapshot cursor identifies a database, computation revision, and committed prefix. Snapshot pages retain that prefix while new documents arrive. Continue a query with both its cursor and after token, then use the snapshot cursor for later changes. Changes carry complete resulting key states, coalesced per key within each batch.

Portable cursors belong to their original database identity and module. Native connections and reopens of the same file with the same module can reuse cursors; a new browser worker or rebuilt database has a new identity and cannot reuse them. Row iterators release transactions between pages. The portable API currently retains all history and exposes no compaction. Callback Database.compact can discard old changes at an explicit caller-selected boundary, expiring older readers while retaining documents for rebuilds.

Numerical reproducibility

Portable payloads, keys, states, and results use finite IEEE-754 doubles, matching JavaScript numbers. Python rejects integer inputs that cannot be represented exactly as a double. Large exactly representable values still use double semantics; encode arbitrary-precision identifiers as strings. Positions and engine sequences must remain in the nonnegative JavaScript-safe integer range. JSON nesting is bounded to 64 levels.

The same compiled AssemblyScript module runs in both native and browser portable hosts, using shared canonical key representation. Neither host adds Python arbitrary-precision arithmetic. Floating-point addition is not associative: arbitrary merge trees can change sum or mean rounding. Preserve input order and the declared partition/merge plan when exact agreement matters. Merge compatible states with disjoint coverage, rather than finalized means.

The callback API's bundled numeric reducers are a separate Rust mathematical kernel compiled to Wasm. Its count and envelope have exact merge contracts within their input bounds; sum and mean have floating-point merge limits. That reducer-only ABI is distinct from the complete AssemblyScript view ABI. A bundled module change can affect each API's cached-state identity through its respective upgrade rules.
